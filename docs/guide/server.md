# The server

What `pd new` writes is a running app. This is what the parts of it are, so that
when you change one you know what you are changing.

The short version: a **stack** of servers, each wrapping the next, with the
innermost one talking to the database. Everything payday enforces is placed
somewhere in that stack on purpose, and the wiring that stacks it is in your
repository rather than behind a function call.

## 1. The stack

A request goes through the gRPC interceptors, then down the stack of servers,
and the innermost one runs the statement.

```
  grpc.Server
    └ interceptors ......... who is calling, how often, what is closed
      └ Gate ............... may this caller do this at all      (generated)
        └ Audit ............ the trail's own service             (generated)
          └ your layers .... your rules                          (yours)
            └ Sink ......... the wall, the minter, the trail     (generated)
              └ ent
```

Three of those are generated by `pd gen` into `server/pd`, and you do not edit
them. `Sink` is the innermost because two things it does have to be: the wall is
a predicate and belongs in the `WHERE` clause, and the trail has to be written
inside the transaction that makes the write it describes.

Everything between is yours. `pd new` writes none of it — an app starts with no
layer of its own and adds one when it has a rule to put there.

The stacking itself is in `cmd/serve.go`, in your repository:

```go
stacked, err := app.Build(walled.WithWatch(w), pd.AuditBuild(), pd.GateBuild())
```

`app.Build` takes the innermost server and then each builder in turn, so **the
last one given handles the request first**. `pd.GateBuild()` is last, which puts
the gate outermost: nothing behind it has to ask again.

That line is ten lines of wiring rather than `pd.Serve(cfg)`, and that is
deliberate. The order of the stack is the most load-bearing fact about an app,
and a framework that supplied it would be hiding the thing a reader most needs
to see.

## 2. The two servers, and why there are two

```go
Walled  app.Server   // what a caller reaches
Ungated app.Server   // what the deployment does its own work through
```

Some of what a deployment does cannot be done from inside a tenant. Creating the
first tenant is the clearest case: there is no tenant to be in yet. Working out
who is calling is another — the resolver has to look up a holder before there is
a frame saying which tenant to look in.

The alternative is a superuser flag, and payday does not have one. A flag is a
rule that opens up whenever the right claim is present, and the set of places it
opens up is not written anywhere. Two server instances is a different thing:
going around the wall means **being handed the instance that has none**, which
is a line of wiring in `cmd/serve.go` that a reader can find.

```go
// what a caller reaches: the wall, then the trail, then the gate
walled, _ := pd.NewSink(client, append(opts, bare.WithScope(pd.Wall()))...)
stacked, _ := app.Build(walled.WithWatch(w), pd.AuditBuild(), pd.GateBuild())

// and the same servers with no wall and no gate
sink, _ := pd.NewSink(client, opts...)
ungated, _ := app.Build(sink.WithWatch(w), pd.AuditBuild())
```

Note that `ungated` still keeps the trail. Going around the wall is not going
around the record of having done so.

If you hand `Ungated` to something a caller can reach, you have removed the
wall for every call it serves. That is the whole risk and it is a grep away.

## 3. Writing a layer

A layer is a struct embedding the generated `Overlay`, which forwards every
service you do not override:

```go
package core

type Core struct {
	api.Overlay
}

func New(next api.Server) Core { return Core{api.NewOverlay(next)} }

func Build() api.Builder { return builder{} }

type builder struct{}

func (builder) Build(next api.Server) (api.Server, error) { return New(next), nil }
```

Then override the one service you have a rule about. The service struct embeds
both the layer and the next server's version of that service, so every method
you do not write goes on through:

```go
type coreRobot struct {
	Core
	api.RobotServiceServer
}

func (s Core) Robot() api.RobotServiceServer {
	return coreRobot{s, s.Next().Robot()}
}

func (s coreRobot) Add(ctx context.Context, req *api.RobotAddRequest) (*api.Robot, error) {
	// your rule, and then s.RobotServiceServer.Add(ctx, req)
}
```

### The one thing that is easy to forget

A layer also has to answer `WithDriver`, which is how a transaction rebinds the
whole stack onto one connection:

```go
func (s Core) WithDriver(drv dialect.Driver) (api.Server, error) {
	next, err := enttx.Rebind(s.Next(), drv)
	if err != nil {
		return nil, err
	}

	return New(next), nil
}

var (
	_ api.Server               = Core{}
	_ enttx.Binder[api.Server] = Core{}
)
```

Every layer writes this and none can inherit it. An overlay holds what is behind
it and has no way to make **itself** again, so a layer that did not write this
would be missing from the rebuilt stack — and the requests inside the
transaction would go around it.

Note that it is `enttx.Rebind(s.Next(), ...)` rather than
`s.Next().WithDriver(...)`. `Next()` gives you the generated `Server` interface,
and `WithDriver` is deliberately not one of its methods: if it were, embedding
`Overlay` would promote it, and the promoted one would rebind the layer
underneath yours and answer with a stack your layer is not in.

And nothing catches it at compile time: `enttx.Rebind` asks at run time, so a
layer without it is `ErrNotBindable` the first time somebody opens a transaction
— a batch, or a multi-write RPC — which is not the day the layer was written.

`pd doctor` looks for exactly this. The `var _` line above is what it prints in
the fix, and it is worth keeping: it turns a signature that drifts later into a
compile error.

### What belongs in a layer, and what does not

| | Where |
| --- | --- |
| "only an admin may erase a Robot" | your layer, or a `gate.Policy` |
| "an alias is lowercased before it is stored" | your layer |
| "a Robot is only visible inside its tenant" | **not yours** — declare `tenanted:` and it is generated |
| "who is calling" | **not yours** — `auth`, in the interceptors |
| "this write is on the trail" | **not yours** — the recorder, inside the transaction |

Do not edit the generated `Gate`. It holds payday's own rule — the wall, and the
rules about Tenant and Holder — and it is rewritten on every `pd gen`. Your
authorization goes in front of it or into the `gate.Policy` you inject.

## 4. The interceptors

The chain is built in `cmd/serve.go` and the order is readable there:

```go
chain := grpcx.Serving(ctx, grpcx.WithDeadline(c.Server.CallTimeout())).
	WithUnary(auth.InterceptorUnary(auth.Plain(), Resolver(s.Ungated), auth.PublicDefault)).
	WithStream(auth.InterceptorStream(auth.Plain(), Resolver(s.Ungated), auth.PublicDefault)).
	WithUnary(grpcx.LimitUnary(c.Server.Limiter(), gate.ByTenant())).
	With(gate.Interceptor(nil)).
	With(s.Watch.Interceptor()).
	WithUnary(grpcx.ClosedUnary(c.Server.Closed()))
```

Who is calling comes first, because everything after it reads the frame.

| | What it does |
| --- | --- |
| `grpcx.Serving` | logging, tracing, panic recovery, and a deadline for a call that named none |
| `auth.Interceptor*` | reads the credential, resolves it, puts a `frame` in the context |
| `grpcx.LimitUnary` | how often one caller may ask; `gate.ByTenant()` is the key |
| `gate.Interceptor` | what this caller may do, as against what they may see |
| `Watch.Interceptor` | publishes what the call changed, **after** it answered without error |
| `grpcx.ClosedUnary` | what is closed to callers entirely — `Patch` and `Apply` by default |

### `auth.Plain` is not for production

`Plain` believes what the caller writes. It is right for a sandbox and for
tests, and it is what `pd new` wires because the alternative is an app that
cannot be run until you have a certificate authority.

`auth` also has `MTLS()` and `Bearer(store)`, and `Seq(hs...)` to try several in
turn. What it does **not** have is a way to issue a credential: `auth.Issuer`
and `auth.Sessions` are seams with a reference implementation (`MemIssuer`) and
nothing wired. Logging in is an HTTP endpoint — see
[§9](#9-serving-a-browser).

### Why `Patch` and `Apply` are closed at the transport

`grpcx.Closed` refuses them by method name, before the stack. Closing them in a
layer instead would close them to the server itself, and the generated code uses
them.

## 5. Configuration

Your config struct is yours. payday supplies the blocks every app has, and you
embed the ones you want:

```go
type Config struct {
	Server config.ServerConfig `yaml:"server"`
	Db     config.DbConfig     `yaml:"db"`
	Otel   config.OtelConfig   `yaml:"otel"`
	Watch  config.WatchConfig  `yaml:"watch"`

	Greet GreetConfig `yaml:"greet"` // and whatever else you have
}
```

And the loader fills in any struct at all:

```go
l := config.For("acme")

var c Config
from, err := l.Load(&c, path, os.Environ())
```

A file, then the environment over the top of it. The order is fixed and
`Load` does both, rather than leaving them to be called in turn — a
configuration read the other way round is one where a deployment sets a variable,
watches the file win, and has nothing to look at that says so.

Inside the file, `${env:NAME}` is resolved before decoding, so a secret can be
named in the file without being written in it.

Environment variable names come from the struct by reflection, so `server.addr`
is `ACME_SERVER_ADDR` for an app whose loader was made with `config.For("acme")`.
`<app> config env` prints the whole list, which is what a `.env.example` should
be diffed against.

### The one setting with no default

```yaml
watch:
  broker: memory
```

`watch.broker` is required, and naming `memory` explicitly is the point. The
in-process broker is correct for one replica and **silently wrong** for two — a
subscriber on one replica never hears about a write on another, and nothing
fails. A required field makes that a thing somebody decided.

## 6. Background work

A layer with something to do on a clock answers `spin.Spinner`:

```go
type Spinner interface {
	Spin(ctx context.Context) error
}
```

`spin.Run` walks what it is handed and runs the ones that implement it. Nothing
declares that it has background work; the ones that do are found.

The alternative — `Spin(ctx)` on the generated `Server` interface — would make
every `Overlay` and every generated server carry an empty method saying "nothing
here", and then "does this layer have background work" is no longer visible in
the code.

A `Spin` that returns kills the process. A sweep loop that stopped quietly is
found days later.

## 7. The database

The ent client is yours to build. `config` hands back a `*sql.DB` and the
dialect rather than a client, because the client is generated into your app from
your schema and payday has no name for it.

```go
db, dialect, err := c.Db.Open(ctx)
drv := entsql.OpenDB(dialect, db)
client := ent.NewClient(ent.Driver(drv))
```

### Migrations

`migrate.Migrations` plans and applies them:

```go
m := migrate.Migrations{Dir: dir, Dialect: s.Dialect, Tables: entmigrate.Tables}

files, err := m.Plan(ctx, dev, "add_robot_labels")  // writes SQL to review
files, err := m.Apply(ctx, s.Db, s.Dialect)         // runs what is pending
```

Mounting these as commands is yours to do, and they belong on **your** binary
rather than on `pd`: they have to link your ent schema, and a deployment should
run its migration with the same image it serves with. `pd new` does not write
them — an app that has not deployed anything yet does not need a migration
directory, and one that has should decide what its commands are called.

The files live in your repository and are reviewed like any other code. Planning
and applying both use the atlas packages ent already depends on; the separately
licensed Atlas CLI is not involved.

### And a check before serving

```go
if c.Db.Migrate {
	err := s.Ent.Schema.Create(ctx)      // development
} else {
	err := migrate.Check(ctx, s.Db, s.Dialect, entmigrate.Tables)
}
```

payday owns part of your schema, so a field added to a holder upstream arrives in
`internal/ent` the next time you generate — and nothing about that is loud. It
compiles, and the tests pass against a database the tests just created. The first
sign of trouble is a column that is not there, in the one handler that reads it.

`migrate.Check` asks whether the database is **not missing** anything, rather
than whether it matches: columns and indexes it does not know about are left
alone.

## 8. The commands

`pd` is the generator. It runs against a checkout and never has your app's
types.

| | |
| --- | --- |
| `pd new <module> [dir]` | writes an app: schema, server, config, and a React page |
| `pd gen [dir]` | regenerates everything from the schema. `--ts` for the client half |
| `pd gen --check` | regenerates and fails if anything moved. This is the CI step |
| `pd entity add <Name>` | a new entity, with a free domain number picked and the tenancy stated |
| `pd doctor` | what would go wrong: missing tools, missing buf deps, an overlay for nothing, a layer that cannot be bound |

The other commands are on **your** binary, because each needs something only
your app can hand over:

| | |
| --- | --- |
| `<app> serve` | the stack above |
| `<app> init` | the first tenant, and somebody in it. It cannot come in through the API — there is no tenant to be in |
| `<app> config` / `config env` | needs your config struct to walk |
| `<app> version` | what build is running |

The last two come ready-made from `payday/pdcmd` — `pdcmd.NewCmdConfig(Loader, c)`
and `pdcmd.NewCmdVersion()` — and the first two are written into your repository
by `pd new`, because their bodies are the stack and the first row.

`pd` is distributed as a `tool` directive in your `go.mod`, so there is nothing
to install and the version is pinned with everything else:

```sh
$ go tool pd gen
```

## 9. Serving a browser

gRPC is not a protocol a browser speaks — not a missing library, a thing the
platform does not expose. `web.New` puts Connect and gRPC-Web in front of the
**same** `*grpc.Server`:

```go
h, err := web.New(c.Server.Http, g)
```

Same handlers, same interceptors, same wall. A call arrives as JSON over POST,
is re-encoded as protobuf, and reaches the handler a gRPC client would have
reached. There is no second door for a rule to be missing from.

Nothing is opened unless `server.http.addr` is set.

Whatever else you serve over HTTP goes on the same mux:

```go
h.Handle("/login", login(s.Ungated))
```

A gRPC path is `/<service>/<method>`, so an ordinary route cannot collide with
one — and `ServeMux` panics rather than shadowing if one somehow does.

Logging in is the case payday left a seam for and cannot fill. `auth` reads a
credential and does not issue one, and issuing is an HTTP endpoint.
